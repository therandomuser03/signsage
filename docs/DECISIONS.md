# SignSage — Decisions Log

Lightweight decision record — one entry per non-trivial choice, not a formal multi-file
ADR process (this is a solo project; the overhead isn't justified). Add to this instead
of relitigating settled questions.

| Decision | Rationale | Status |
|---|---|---|
| FastAPI over Flask for the backend | Small jump from the earlier prototype's Flask experience; native async/WebSocket support without needing Flask-SocketIO; landmark streaming benefits from a persistent socket over per-request HTTP | Adopted |
| Plain Transformer, not GAT, for the Sign->Text model | SMART Objective 1 only commits to "Transformer-based"; GAT adds graph-construction complexity and a likely new dependency (PyTorch Geometric) for a niche gain — revisit only if a flat Transformer's accuracy gap points specifically at needing explicit joint-relationship modeling | Adopted |
| GRU baseline before Transformer | Prove landmarks->text can learn any signal at all on the smallest possible model before investing in a bigger architecture | Adopted |
| Single-device MVP, no two-device WebSocket relay / room codes | Primary use case is same-room conversation; relay infra doesn't test translation quality; defer until single-device MVP proves useful and remote use is actually demonstrated as needed | Adopted |
| SQLite over Turso for persistence | No distributed/edge-latency problem exists yet; add Turso only if SQLite genuinely becomes a bottleneck | Adopted |
| Groq as primary LLM, Ollama as offline fallback | SMART Objective 2 measures latency; a local LLM on modest hardware would dominate and distort that measurement | Adopted |

| **Training moved to Kaggle Notebooks on GPU (T4), replacing local CPU-only training** | CPU training did become the blocker this log's earlier row anticipated: a `d_model=192` Transformer plus a generative pose decoder over 1629-dim inputs is not a one-evening CPU run, and the guide's completion date (2026-09-05) leaves no room for it. Kaggle gives a free T4 with no Tailscale-into-a-disposable-VM problem (unlike the rejected Colab bridge) because the data no longer travels through the home network at all — see the streaming row below. `USE_AMP` (fp16 autocast + `GradScaler`) is enabled only on CUDA; fp16 rather than bf16 because T4 is Turing and has no fast native bf16 tensor-core path. `BATCH_SIZE` 16 and `GRAD_ACCUM_STEPS` 1 on GPU, versus 8 and 4 on CPU | Adopted |
| **Pose data streamed from HuggingFace as a virtual multipart ZIP64 instead of being uploaded to Kaggle as a Dataset** | The obvious Kaggle move — reduce the archive to ~140-150 GB and upload it as a Kaggle Dataset — costs days of upload before a single epoch runs, and still wouldn't fit comfortably. Instead the notebook opens the four `iSign-poses_v1.1_part_a{a,b,c,d}` files as one seekable virtual file (`RemoteConcatFile`), lets Python's `zipfile` read the ZIP64 central directory over HTTP range requests, and fetches only the members the selected train/val/test rows actually need. Nothing is extracted; only the 9.81 MB CSV is downloaded outright. Real costs, stated plainly: it needs Kaggle Internet enabled and an `HF_TOKEN` secret; per-member latency (~8 sequential 256 KB range requests for a ~1.9 MB pose file, at `NUM_WORKERS=0`) makes the cold-fetch phase, not GPU time, the schedule bottleneck. The completed bounded Kaggle run now provides evidence that the virtual archive/member access path works in practice. Cell 8 remains the early structural check, while cold-fetch latency remains the main operational caveat | Adopted, **validated by completed bounded Kaggle run** |
| **Structured project knowledge repository: SQLite for the queryable record, JSON for the portable manifest** | "Dataset -> train -> done" leaves no evidence trail, and an M.Tech artifact needs to answer *which* experiment produced *which* checkpoint under *which* hyperparameters and dataset version. SQLite (7 tables: `runs`, `dataset`, `splits`, `experiments`, `metrics`, `artifacts`, `observations`, all keyed on `run_id`) holds the relational history because those are genuinely join-shaped questions; JSON holds the flat, portable per-run snapshot (config, vocab info, run summary) that the backend can read without opening a DB. Deliberately **not** described as a RAG knowledge base — it is experiment provenance, not retrieval-augmented anything, and calling it the latter would oversell it. Writers are idempotent so re-running a cell replaces rather than appends (see DATA_MODEL.md); `knowledge_observation` is the one deliberate exception | Adopted |

This confirms the training/output pipeline reached artifact creation. | Groq gloss step (Part 12) switched from `llama-3.1-8b-instant` to `openai/gpt-oss-20b`, with `reasoning_effort="low"` and a try/except fallback to the naive heuristic | Groq deprecated and shut down `llama-3.1-8b-instant` on 2026-08-16 — the hardcoded model in the notebook no longer exists. `gpt-oss-20b` is Groq's own recommended replacement and is a small/fast production model (unlike preview-tier alternatives); `reasoning_effort="low"` avoids default chain-of-thought overhead for what's a mechanical rewrite task, relevant since SMART Objective 2 measures latency. The try/except means a future Groq deprecation degrades gracefully to the naive heuristic instead of crashing the notebook | Adopted |
| Local Ollama fallback model, if/when implemented: `llama3.2:3b` (or `qwen2.5:3b-instruct` as an alternative) | Dev machine has 8 GB RAM with ~3 GB typically free; 7-8B class models (~4.5-5 GB at Q4) would force constant swapping alongside the backend/frontend/MediaPipe also running. 3B-class instruct models are the smallest tier that reliably follows "reply with only the gloss" without extra commentary. Not yet wired into the notebook — only Groq-or-naive-heuristic exists in code today | Proposed, not yet implemented |
| Disk-backed normalized-pose cache (per-UID, float16) reused across epochs/restarts | One `.pose` per UID means no within-epoch reuse, but every epoch would otherwise re-parse (locally) or re-fetch (on Kaggle) the same training UIDs. The loader normalizes each UID once and caches a small float16 array under `POSE_CACHE_DIR`; writes are temp-file + `os.replace` (atomic) and a load failure is treated as a cache miss, so a killed run self-heals. Payoff differs sharply by environment: locally it does not reduce random-access seek count on the mechanical HDD, so the speedup is real but modest; on Kaggle it eliminates repeat HTTP range fetches, which is the dominant cost there, so it matters far more | Adopted |
| Kaggle's pose cache lives in `/kaggle/temp/signsage_cache/`, not under `DATA_DIR` in `/kaggle/working/` | `/kaggle/working` is committed as the notebook's saved output and counts against the 20 GB output limit, so a multi-GB regenerable cache there would bloat every saved version and compete with the checkpoints and reports that are actually meant to be downloaded. `/kaggle/temp` is session scratch on the same instance disk. Accepted cost, stated explicitly: the cache does **not** survive the session, so a second Kaggle session re-fetches every pose from HuggingFace, and an interrupted run pays the full cold-fetch cost again on restart. Flip `CACHE_ROOT` back to `DATA_DIR / "cache"` if restart speed ever matters more than output size (~2-3 GB at current sample limits: 160 frames × 1629 features × 2 bytes ≈ 521 KB per sample). Local mode is unchanged — persisting the cache next to the dataset is the whole point there | Adopted |
| Gradient accumulation (`GRAD_ACCUM_STEPS`): 4 on CPU, 1 on GPU | Simulates a larger effective batch than `BATCH_SIZE` without holding more than one small batch in memory at once. On the CPU path it was included mainly for completeness rather than to fix a measured bottleneck: on a `d_model=192` model the RAM difference between batch 8 and effective batch 32 is negligible against the 4 GB budget, which is dominated by data loading and Python/OS overhead, not activation memory. On the Kaggle T4 there is enough VRAM for `BATCH_SIZE=16` outright, so accumulation is switched off — it would only add optimizer-step latency for no memory benefit | Adopted, low-impact |
| `RUN_MODE` is derived from the environment (`"kaggle"` if `IS_KAGGLE` else `"smoke"`), with `psutil` RAM/swap monitoring | Smoke mode (300/60/60 rows) validates the whole pipeline cheaply before any full-scale run; the monitor prints a warning above 30% swap so the 4 GB HDD-backed local machine's swapping is caught early rather than silently stalling a run. Kaggle mode (2000/300/300, 5-6 epochs) is deliberately a *bounded first GPU validation pass*, not a claim that 2,000 examples suffice for a thesis result. Note `"full"` (all rows, 20-25 epochs) is defined but **unreachable without editing the notebook** — that is intentional, so nobody launches a multi-hour cold-fetch-plus-training run by accident on the first attempt | Adopted |
| In-notebook Phase-1/2 live demo (FastAPI/WebSocket server + MediaPipe HTML client, formerly Section 18 behind `RUN_LIVE_DEMO=False`) **removed from the notebook entirely** | A flag defaulting to off still left serving code, an INT8-quantization path, and an HTML client inside the research artifact — which invited exactly the "just flip it on" shortcut AGENTS.md's core rule exists to prevent, and made the notebook's scope look like the application's scope to anyone reading it. Application serving belongs to Phase 1's backend, built from modules extracted from this notebook, not to the notebook. Removing it is now enforced by absence rather than by a flag: no `RUN_LIVE_DEMO`, no FastAPI, no INT8 quantization anywhere in the file. The divergence lists in API.md and DESIGN.md are kept as a record of what that spike got wrong, so the real backend doesn't repeat it | Adopted |
| `tqdm` progress bars on every training/eval loop; explicit cache-prewarm pass retained but **off by default** (`PREWARM_CACHE = False`) | A cold first epoch has to populate the pose cache before printing anything, which is indistinguishable from a hang — this is what a stuck-looking cell turned out to be in practice locally, so visible per-batch progress stays.
